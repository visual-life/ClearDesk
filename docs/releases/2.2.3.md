# ClearDesk 2.2.3

发布日期：2026-10-27（2.2.2 之后的修补版本）

## 修复

### 1. Dock 里有的程序不显示图标（Antigravity、系统「设置」等）

现象：Dock 里正在运行但没有固定的程序，图标是空白，或者是一个通用的「窗口」图标，提示文字还是「Application Frame Host」。

原因（两处，都在 2.2.2 之前就存在，2.2.0 起 Dock 只靠「进程 exe」取图标）：

1. **失败被永久缓存。** `IconCache` 在后台线程取图标，取不到就把 `null` 存进缓存，之后同一个程序一律显示空白，直到重启 ClearDesk。程序刚启动、exe 暂时被占用、外壳图标缓存还没准备好等瞬时失败都会这样。
2. **UWP / 打包应用的窗口属于 ApplicationFrameHost.exe。** Dock 取的是窗口所属进程（ApplicationFrameHost.exe）的 exe 图标——它没有自己的图标，显示的是系统默认的空白窗口；名称也是它的文件说明「Application Frame Host」。

修复：

- 新的图标解析链（`AppIcons`）：UWP 宿主窗口先取「开始菜单里该应用的图标」（按 AppUserModelID 走 shell:AppsFolder，256 像素）；其余程序先取 exe 图标（跳过系统「通用应用」图标），再取窗口自己的图标（WM_GETICON 大 / 小 / 小2 与窗口类图标，取最大的），再取 AppUserModelID 图标，再取开始菜单里指向该程序的快捷方式图标，最后才是 exe 的通用图标。全透明的图也算失败。
- **失败不再缓存。** 取不到时显示一个带首字母的彩色图标，并在 2、5、15、45 秒后自动重试（共 4 次），每次 Dock 重建也会再试；找到后直接替换同一个控件。
- UWP 应用的名称和图标来自「开始菜单」里的应用（例如「设置」），不再显示 Application Frame Host。
- `ClearDesk.exe --dock-diag` 现在会逐个列出正在运行的应用以及每一级图标来源的结果，并把每级图标存成 PNG（`dock-diag-icons` 文件夹），方便排查。

验证：在这台电脑上用 `--dock-diag` 实测——「设置」（ApplicationFrameHost）→ 取到 256 像素的包图标，名称「设置」；Antigravity → exe 图标 256 像素、窗口图标 512 像素。新增 16 项测试（解析顺序、空白 / 通用图标、失败不缓存、重试、UWP 包图标）。

**没有复现的部分：** 这台电脑上 Antigravity 当前能正常取到图标，所以「Antigravity 空白」的那一次瞬时失败没能在现场复现；修复覆盖的是这类失败的机制（失败不缓存 + 有备用来源 + 自动重试）。

### 2. 文字不清晰

我们逐项对比了 2.2.1、2.1.1 和 2.2.2 的渲染（把组件在屏幕上真实画出来再截图，同一个灰色背景上量化）：**默认大小、有边框的组件，2.2.1 与 2.2.2 的清晰度数值完全一致**，没有代码层面的回退；变糊来自无边框模式（2.2.2 新增）和非默认尺寸这两种用法。

原因：

1. **无边框文字阴影太糊（主要原因，已量化）**：2.2.2 的阴影模糊半径 7、不透明度 0.6、性能优先渲染，细体字（Segoe UI Light）周围罩了一圈灰雾，看起来像字发虚。屏幕实测，时钟数字周围被阴影压暗的面积（每个文字像素对应的暗区像素数）：无阴影 0.00，2.2.2 为 **3.34**，2.2.3 为 **1.10**。
2. **组件不是默认尺寸时，文字是先按默认大小排版再整体放大的**，笔画落在小数像素上，边缘变成两个像素的灰边（默认大小的组件不受影响）。

修复：

- 无边框文字阴影改为：模糊半径 2.5、偏移 1、不透明度 0.55、高质量渲染——仍有阴影（深色壁纸 / 亮色壁纸上都可读），但暗区面积降到原来的三分之一。有测试断言：2.2.3 的暗区小于 2.2.2，且大于无阴影。
- 为第 2 点做了「文字块按最终字号排版再用 1/缩放 缩回」的实验（`CrispText`，对所有组件的所有文字块生效，自动处理后来添加的文字、组件自己改字号、缩放回 1 时恢复）。**实测结论：没有稳定收益**——在 5 种组件 × 3 种放大倍数（15 组）里，亮色笔画「完全点亮」比例的平均变化约 +0.004（9 组变好、6 组变差，时钟 ×1.35 明显变差），属于噪声。所以**默认关闭**（不改变任何组件的排版），只保留代码和测试，设置环境变量 `CLEARDESK_CRISPTEXT=1` 可以打开继续试。我们没有把一个没有被测量证实的改动默认发给所有组件。

验证与对比图：`docs/images/2.2.3`（`shadow-before-after.png`：2.2.2 / 2.2.3 / 无阴影的时钟实拍，`shadow-before-after-zoom.png` 放大 3 倍）；测试输出里的 `text shadow (screen)` 行是上面的数字。

局限：这一项只在 100% 缩放的这台电脑上量过；125% / 150% 系统缩放下没有实机对比（离屏渲染无法复现系统 DPI 的取整）。如果你的屏幕是 125% / 150% 且仍觉得字发虚，请告诉我们系统缩放比例和是哪个组件，需要单独看。

### 3. 退出 TranslucentTB 后再打开 ClearDesk，提示「任务栏组件校验失败」无法启动

现象（用户反馈）：在任务管理器里结束 TranslucentTB.exe，再打开 ClearDesk，弹出「任务栏组件校验失败」，ClearDesk 起不来。

原因：「透明任务栏」是 ClearDesk 自带的可选组件（TranslucentTB）。2.2.2 及以前，ClearDesk **启动时**就在主流程里校验 `taskbar` 文件夹里的每个文件（SHA-256 对照 `verified.sha256`），任何一项不符、缺失、被占用、被安全软件移走，都会直接抛异常，走到「ClearDesk 启动失败」对话框并退出——一个可选功能出了问题，整个程序都不能用；而且「透明任务栏」开关是保存在设置里的，所以每次启动都会再失败一次，用户只能手动改设置文件。结束 TranslucentTB 本身不会改动文件内容，所以真正让校验不通过的一般是：组件文件被替换 / 覆盖了一半（运行中的 exe 被占用，覆盖解压时旧 exe 留下而清单是新的）、被安全软件隔离或改写、或文件正被扫描占用；在我们这台电脑上，正常安装的两份 `taskbar` 文件夹校验都是通过的，所以**没有能直接复现「结束进程后校验失败」这个哈希不匹配本身**——但可以确定：不管是哪种原因，2.2.2 的处理方式（致命退出）是错的。

修复（2.2.3）：

- 启动不再因为可选组件而失败：`Services.Apply()` 外加保护，组件校验失败只记日志、弹一条不阻塞的托盘提示（「透明任务栏暂不可用…ClearDesk 其他功能不受影响」），ClearDesk 照常启动。窗口事件监听失败（最小化动画）同样不再致命。
- 按需校验：只有在要启动透明任务栏时才校验；校验时用共享方式读文件（运行中、正被扫描的文件也能读），被占用就重试几次，仍被占用算「暂时不可用」而不是「损坏」。
- 自动修复：第一次校验通过后，把完好的组件备份到 `%LOCALAPPDATA%\ClearDesk\taskbar-good`；之后发现文件缺失、被改动、被隔离、清单缺失或无效，先从备份还原（正在被占用的文件先改名挪开再写入），还原后再次校验通过就正常启动。
- 没法修复时：关闭这个功能（不改你保存的开关），并在约 1 分钟、5 分钟、30 分钟后自动再试；在设置里把开关关掉再打开也会重试。
- 你自己在任务管理器里结束了 TranslucentTB：ClearDesk 发现后只记一条日志，不会自动再拉起来跟你对着干（下次启动 ClearDesk，或把开关关掉再打开，才会重新启动它）；过期的恢复状态文件不会影响下一次启动（按进程路径核对，不会误关别的进程）。
- 已有独立运行的 TranslucentTB 时：只给出提示，不改它的配置（和以前一致，但不再导致 ClearDesk 无法启动）。

测试（`V223TaskbarTests`，20 项，用一个假的组件目录，不碰真实的 TranslucentTB）：健康启动并保留完好备份；进程被结束后的过期状态；文件损坏 / exe 缺失（相当于被隔离）/ 清单缺失 / 清单无效 → 从备份还原并启动；文件被独占锁定 → 不崩溃、不启动、稍后重试，锁释放后启动；文件正被别处打开且已损坏 → 改名挪开后还原；损坏且无备份 → 返回原因而不抛异常（旧的 `Start()` 仍抛异常，兼容旧调用）；独立 TranslucentTB 在运行；`DesktopServices` 启动路径不抛异常、修好后重试成功、运行中 TranslucentTB 被结束后 ClearDesk 继续运行。
