# ClearDesk 2.2.4

发布日期：2026-10-28（2.2.3 之后的修补版本）

两个用户反馈：**① 时钟和性能组件重启后回到默认位置；② 透明任务栏提示「组件文件与校验清单不一致：TranslucentTB.exe（没有可用的完好备份）」。**
下面分开写：哪些是**在测试里复现 / 实测证明**的，哪些是**根据代码推断**的。

## 一、时钟 / 性能组件重启后回到默认位置

### 先说结论（诚实版）

- **没有找到「只针对时钟和性能」的代码。** 这两个组件和其他组件用同一套保存 / 恢复代码（`Settings.Widgets["clock"]` / `["performance"]`，字段 X / Y / Width / Height）。它们默认是开启的，所以设置一旦被重置，最先在它们身上看到。
- **没有在这台电脑上复现「用户重启后回到默认位置」本身。** 我们复现、并用测试证明的是下面几条「会丢位置」的通道在 2.2.3 的代码里确实存在（读代码得出）：2.2.3 没有这些保护，2.2.4 加了并有测试。哪一条是该用户遇到的那一条，**无法从这里确定（推断）**；2.2.4 把这几条都堵上了，并且会在 `errors.log` 里记下发生过什么。

### 2.2.3 代码里会让位置丢失的通道（读代码确认）

1. **设置文件读不出来就悄悄用默认值，并且之后会把真文件覆盖掉。** 启动时 `settings.json` 若被占用（开机时杀毒软件正在扫描、云盘同步、另一个进程刚写完）或是 0 字节 / 被截断（断电、强制关机时正好在写），2.2.3 只读一次、失败就用默认设置运行，而且不会去读 `settings.json.bak`；下一次保存（拖动任何组件、改任何设置）就把真文件覆盖成默认值。——这是最符合「重启后回到默认位置」的一条（推断为最可能）。
2. **保存没有真正落盘、遇到「拒绝访问」不重试。** 2.2.3 的保存用「写临时文件再替换」，但没有 flush 到磁盘，只重试「文件被占用」一种错误；杀毒软件锁文件常见的是「拒绝访问」，一次失败就放弃，内存里的新位置丢在下次启动。
3. **没有处理注销 / 关机。** 位置在拖动结束时保存，没有「会话结束」时的补充保存；关机时进程被系统结束，改动若还没写入就丢了。
4. **屏幕外的保存位置被放到左上角（看起来像默认）。** 2.2.2 起只在视觉上救回，但救回到工作区左上角（20,20），用户看到的就是「回到了默认位置」。
5. **多显示器、不同缩放：** 位置以 DIP 保存，不同缩放的显示器上同一数值可能对应不同的实际位置；系统在登录时挪动窗口后，2.2.2 的稳定期纠正是按 DIP 的。

### 2.2.4 的修复

- **新的设置文件读写层（`ConfigStore`）**：
  - 读：用共享方式读，被占用就重试（约 3 秒）；`settings.json` 读不出来 / 为空 / 损坏，依次尝试 `settings.json.bak`、`settings.json.tmp`；从备份恢复后立即把 `settings.json` 修好；
  - **读不出来（被占用）时只用默认值临时运行，绝不覆盖那个文件**，之后每 4 秒重试，能读时直接换成真设置并重建组件（位置就回来了）；
  - 写：先写临时文件并 flush 到磁盘，校验能读回，再原子替换（保留 `.bak`）；「文件被占用」「拒绝访问」都重试；仍失败就留在「未保存」状态，4 秒后再试，退出时再试，并写 `errors.log`；
  - 位置里出现 NaN / 无穷大等无效数值，只重置该组件，不影响其他组件和整个文件。
- **随时保存**：用户拖动 / 调整大小后约 0.5 秒保存（连续拖动合并），拖动结束仍立即保存；之后直接杀进程也不会丢。
- **会话结束时保存**：`Application.SessionEnding`、`SystemEvents.SessionEnding`、窗口收到 `WM_QUERYENDSESSION` / `WM_ENDSESSION`、进程退出、应用退出都会先保存。
- **不再把位置重置到默认角落**：保存的位置不在任何显示器上时，只把窗口显示到离它**最近的可见位置**，保存的值不改，显示器回来后自动回到原处。只有数值本身无效（NaN）才用默认位置。
- **像素级核对**：用户移动组件时同时记下设备像素位置和当时的 DPI；稳定期结束后，若 DPI 没变而窗口不在记录的位置，就放回去（解决多显示器不同缩放的取整偏差）。DPI 变了不使用这条记录。
- **旧配置迁移**：2.0.x / 2.1.x 的设置里组件键大小写不一（`Clock` / `Performance`）会合并为小写键，位置保留；没有组件记录的旧文件按默认放一次再保存。`ConfigVersion` 升为 6。
- **设置文件是 0 字节且没有备份**：保留一份 `settings.json.corrupt-时间` 副本再用默认设置，不静默丢弃。

### 测试（`V224Tests`，都能在无人值守的测试里跑）

- 保存后不正常退出（模拟被杀）再启动：位置完整保留；
- 注销 / 关机：`FlushSave` 与 `WM_ENDSESSION` 都会把尚未保存的改动写盘；
- 新用户第一次运行：无文件被识别为「全新」；
- 旧版配置（大小写不一的键、2.0.x 无组件记录）；
- 用户拖动两个组件后重启：窗口出现在保存的位置；
- 设置文件被占用读取 / 瞬时占用后重试成功 / 写入遇到占用 / 拒绝访问 / 真实的 300 毫秒独占锁；
- 0 字节、截断、损坏且无备份；被占用时不会覆盖原文件（`Program.Save`）；
- NaN / 无穷大；屏幕外位置就近夹取；像素核对四种情况。

## 二、透明任务栏：「组件文件与校验清单不一致：TranslucentTB.exe（没有可用的完好备份）」

### 已证明的事实（读代码 + 实测）

- 2.2.3 只校验 `ClearDesk 所在文件夹\taskbar`，对照**同一文件夹里的 `verified.sha256`**；没有任何内置的「出厂」副本可比。`%LOCALAPPDATA%\ClearDesk\taskbar-good`（完好备份）**只在校验第一次通过之后才建立**——所以「第一次就不一致」时必然提示「没有可用的完好备份」，这个提示本身就说明这台电脑从来没有通过过校验。
- ClearDesk 自己**不会写** taskbar 里的文件（更新器整体替换文件夹除外）；1.8.2 到 2.2.3 所有版本的清单完全相同（5 个文件的哈希未变），发布的 zip 解压后 5 个文件全部与清单一致（已逐个验证）。所以「TranslucentTB 版本不同」**不是**清单变了：同一份 ClearDesk 里的 TranslucentTB 一直是 2026.2.0.d4636e4。
- 用户截图里另一个弹窗（标题 TranslucentTB，「TranslucentTB 已更新。请重启 Windows 以使用最新版本。」）是 **TranslucentTB 自己**的提示（上游源码 `IDS_RESTART_REQUIRED`）。它的触发条件是：资源管理器里还加载着旧版本的 `ExplorerTAP.dll` / `ExplorerHooks.dll`（TranslucentTB 把它们复制到 `%TEMP%\TranslucentTB` 再注入资源管理器）。**卸载 Microsoft Store 版 TranslucentTB 不会把已经注入资源管理器的 DLL 卸掉**，需要注销 / 重启电脑（或重启资源管理器）。双击 `taskbar\TranslucentTB.exe`「能启动」也符合这一点：它能启动，但注入失败时会弹这个提示并退出。

### 推断（无法在这台电脑上证明）

「组件文件与校验清单不一致」那条提示，说明该用户那台电脑上 `taskbar` 文件夹里**至少有一个文件的 SHA-256 与清单不同**。可能原因（按可能性）：他用 Store 版或另一版 TranslucentTB 覆盖 / 替换了其中的文件，或解压 / 复制时被安全软件或网盘改写；他「重新复制 taskbar 文件夹」若复制自同一台电脑的已被改动的副本，结果不变；ClearDesk 实际运行的文件夹可能不是他检查的那个（开机自启动指向另一个旧文件夹）。**这些无法从这里判断**，所以 2.2.4 加了精确的诊断，下次一次就能看清。

### 2.2.4 的修复

- **内置出厂副本**：`ClearDesk.exe` 里内置 taskbar 组件（5 个校验文件 + 清单 + TranslucentTB 版本号）。校验的依据是这份出厂副本，**文件夹里 `verified.sha256` 过期、缺失、格式不对（BOM / CRLF）都不再影响判断**。
- **从出厂副本修复，不再需要「完好备份」**：不一致、缺失、被隔离时，先用 `taskbar-good` 备份，没有就用内置出厂副本直接写回 `taskbar` 文件夹（正被占用的文件先改名挪开），再校验、再启动。
- **安装文件夹写不进去 / 修不好**（只读、权限、杀毒锁）：把出厂副本放到 `%LOCALAPPDATA%\ClearDesk\taskbar-run` 并从那里启动。
- **可选「允许使用未通过校验的 TranslucentTB」**（设置里，**默认关**，有醒目的风险说明）：只有 TranslucentTB.exe 的版本号与内置版本相同、Authenticode 数字签名有效、仅哈希对不上时才放行（例如被其他工具重新打包）；改过内容的文件不放行。放行时错误码 `TB-09` 并写日志。
- **精确诊断写进 `errors.log`**：检查的文件夹、每个文件的期望 / 实际 SHA-256、大小、修改时间、文件版本、数字签名、属性、是否带「来自网络」标记、校验依据、备份与每用户副本状态、正在运行的 TranslucentTB（路径）、资源管理器里已加载的 ExplorerTAP.dll 路径与哈希。
- **提示带短代码和「打开日志」**：`TB-01` 缺少校验清单、`TB-02` 文件缺失、`TB-03` 哈希不一致、`TB-04` 文件被占用（暂时）、`TB-05` 校验清单无效、`TB-06` 启动失败、`TB-07` 已有独立的 TranslucentTB 在运行、`TB-08` 组件启动后很快退出（常见于上面说的「需重启 Windows」）、`TB-09` 按设置放行了未校验的组件。点托盘提示即可打开日志。
- **「修复透明任务栏组件…」**：托盘菜单和 设置 → 任务栏与窗口 各有一个入口：重新释放内置副本并显示检查结果。
- **`ClearDesk.exe --taskbar-diag`**：只读，输出同样的诊断到控制台和 `taskbar-diag.txt`，另外列出开机自启动指向哪个文件夹、有哪些 ClearDesk 在运行、是否与当前文件夹一致。
- 新增：组件启动后 30 秒内以非 0 退出，会提示 `TB-08` 并建议重启 Windows。

### 测试（`V224Tests`，用假的组件目录，不碰真实 TranslucentTB）

文件夹清单过期但文件正确 → 仍能启动；换了另一个 TranslucentTB.exe（版本不同）→ 判为 `TB-03`，从出厂副本修复后启动（2.2.3 在这里停下并提示「没有可用的完好备份」）；运行期被改动的文件；安装文件夹不可用 → 用每用户副本；BOM + CRLF 清单；出厂副本自身损坏时不用它；放行选项（关闭时拒绝；开启 + 签名有效 + 版本相同 → 放行；签名无效 / 版本不同 → 仍拒绝）；诊断文本包含文件夹和每个文件的期望 / 实际哈希；短代码；没有出厂副本时给出 `TB-03` 和完整诊断。

### 给用户的恢复步骤（请把这几步发给他）

1. 先**重启电脑**（或注销再登录）——这样资源管理器里旧的 TranslucentTB DLL 才会被卸掉；重启后**不要先去手动运行 `taskbar\TranslucentTB.exe`**。
2. 退出所有 ClearDesk 和 TranslucentTB，用 2.2.4 的完整文件夹（解压到新位置，不要覆盖旧文件夹），确认开机自启动指向这份。
3. 打开 ClearDesk → 托盘右键「修复透明任务栏组件…」（或 设置 → 任务栏与窗口 → 修复并检查），再开启「透明任务栏」。
4. 若仍提示失败：按提示点开日志，或运行 `ClearDesk.exe --taskbar-diag`，把 `taskbar-diag.txt` 发给我们；里面写明了每个文件的实际哈希、是否被改过。
